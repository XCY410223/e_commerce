# 促销活动上线与运维手册

## 1. 当前活动范围

| 活动 | 规则标识 | 交易行为 |
|---|---|---|
| 新客立减 20 元 | `new-customer` | 激活后幂等发券，首单使用，30 天有效 |
| 生鲜满 99 元免运费 | `free-shipping` | 按商品活动价小计判断，减免标准运费 10 元 |
| 周末限时 5 折 | `weekend-sale` | 仅周末和指定分类/SKU 生效，不能与新人券叠加 |

“邀请好友得优惠券”活动已下线：默认规则和首页入口不再创建，迁移 `promotion.0002_remove_invite_campaign` 会停用并软删除已有入口；邀请模型、历史邀请记录和已发奖励券保留用于审计。`PROMOTION_REFERRAL_ENABLED` 默认关闭，只有同时存在启用中的 `referral_reward` 规则时，注册邀请和用户中心入口才会恢复。

## 2. 上线顺序

1. 备份数据库，发布代码并执行 `python manage.py migrate --noinput`。
2. 执行 `python manage.py init_promotions`，补齐三条默认规则并关联首页入口。
3. 执行 `python manage.py check`、`python manage.py makemigrations --check --dry-run`、`python manage.py test -v 2`。
4. 启动测试环境，确认首页、三个活动页、商品列表、商品详情、购物车、确认订单和订单详情价格一致。
5. 使用 `PAYMENT_PROVIDER=mock` 跑一遍下单、支付、取消；真实渠道另用沙箱验证异步通知。
6. 先开启免运费和新客券，观察至少一个完整下单周期，再确认周末折扣时间窗。
7. 执行 `python manage.py promotion_status --strict`，确认没有未关联入口、失效入口或金额快照不一致。

## 3. 紧急开关

| 场景 | 操作 | 影响 |
|---|---|---|
| 算价服务异常 | 设置 `PROMOTION_PRICING_ENABLED=0` 并重启 Web | 新订单回退原价与标准运费，历史订单快照不变 |
| 优惠券异常 | 设置 `PROMOTION_COUPON_ENABLED=0` 并重启 Web | 停止发券和新券核销，已发券保留 |
| 单个活动异常 | 后台将对应 `Promotion.is_active` 设为否 | 新订单立即停止命中，其他活动不受影响 |
| 首页文案异常 | 后台停用或删除对应 `IndexPromotionBanner` | 仅隐藏入口，不影响已参与订单 |
| 邀请活动残留入口 | 保持 `PROMOTION_REFERRAL_ENABLED=0` | 注册邀请绑定和用户中心邀请区块自动关闭 |

环境变量开关调整后需要重启 Web 进程；后台活动开关依赖数据库查询，无需重启。

## 4. 监控指标

优先接入以下五项，建议每 5 分钟采集一次：

| 指标 | 数据来源 | 异常建议 |
|---|---|---|
| 算价失败率 | Web 日志中的 `PricingError`、下单失败提示 | 连续升高时关闭最近变更的活动 |
| 订单金额不一致 | `promotion_status --json` 的 `orders.amount_mismatches` | 大于 0 立即暂停对应活动并核对快照 |
| 支付成功率 | 支付日志 `订单支付成功` 与创建订单数 | 与基线相比明显下降时核对 `total_pay` 和渠道金额 |
| 优惠券核销率 | `UserCoupon` 状态统计、发券/核销日志 | 异常重复使用或无法核销时关闭券开关 |
| 邀请奖励发放数 | `Referral` 状态统计、`邀请奖励已发放` 日志 | 当前活动已下线，默认应无新增；异常时保持开关关闭并排查旧链接 |

巡检命令：

```bash
python manage.py promotion_status --hours 24 --strict
python manage.py promotion_status --hours 24 --json
```

`--strict` 在发现入口未关联、入口指向停用/过期规则或订单金额快照不一致时返回非零状态，可直接作为定时任务告警条件。未来才开始的周末活动不会被误报。

## 5. 回滚策略

1. 优先关闭活动开关或 `PROMOTION_PRICING_ENABLED`，不要先回滚数据库迁移。
2. 新订单回退原价后，确认购物车、确认页和支付金额均重新计算；历史订单继续使用已保存快照。
3. 若必须回滚代码，保留 `OrderInfo`、`OrderGoods`、`OrderPromotion` 和 `UserCoupon` 的新增字段与数据，不要执行破坏性迁移。
4. 若单个活动配置错误，后台停用并修正规则，确认无新订单命中后再恢复；不要物理删除已产生订单快照的活动。
5. 支付已完成但金额或权益异常时，不直接改库；保留日志、订单号和渠道流水号，走人工退款/对账流程。

## 6. 责任边界

| 角色 | 责任 |
|---|---|
| 后端负责人 | `build_quote`、订单事务、支付校验、快照和回滚开关 |
| 前端负责人 | 活动价、划线价、优惠明细和错误提示的一致性 |
| 运营 | 活动时间、范围、门槛、叠加规则和首页文案配置 |
| 测试 | 边界金额、叠加、库存、重复提交、支付篡改和历史订单回归 |
| 运维/DBA | 迁移备份、监控采集、Redis/MySQL 可用性和日志留存 |
| 值班负责人 | 按指标触发开关、组织对账和决定是否回滚代码 |

## 7. 已知限制

- 配送区域尚未建模，免运费按全国地址统一判断；上线前需运营确认是否接受。
- 商品级活动的每人限次字段暂未参与首期规则，周末折扣按订单实时计算。
- 退款只覆盖未支付取消时的退券；已支付退款、部分退款和奖励券回收需接入售后流程。
- 活动自然到期不会主动写数据库，首页和列表最多保留一个缓存 TTL 的旧展示；结算与提交始终按服务端当前时间重算。
